Artifact Description (AD) for form submission. Paper: Drava: An Event-Driven Runtime for Scientific Pipelines. Anonymized for double-blind review; do not add de-anonymizing repository or institution URLs until the paper is de-anonymized.

Artifact Identification

Contributions and role of the artifact. This paper contributes Drava, an event-driven runtime for edge scientific streaming pipelines, together with its callback-based programming model, a runtime that owns microbatching, dispatch, transport, placement, and per-stage observability, an agentic (ytopt) configuration search, and an evaluation on PtychoNN ptychography and TomoGAN tomography against a PvaPy baseline. The computational artifact realizes every one of these claims: it contains the Drava runtime (C/C++ on the XKRT tasking runtime with Python bindings), the two application pipelines, a PvaPy single-record and HPC-distributor baseline for PtychoNN, the agentic search driver, and the benchmark and plotting scripts that regenerate each figure and table in the paper. Running the artifact reproduces the throughput, end-to-end latency, GPU+CPU energy, and configuration-search results reported in the Evaluation section.

Software architecture. Drava is a layered runtime. Applications register per-stage callbacks through a C or Python API; a YAML configuration binds each stage to its transport, batching policy, and thread team without changing application code; and an execution engine performs I/O, microbatching, work-stealing task dispatch, and metrics collection. Stages exchange events, each carrying a unique identifier, timestamp, and payload, over two interchangeable transports: Unix sockets for intra-node communication and NATS JetStream (publish/subscribe) for streaming across nodes. Each stage runs as a process with an internal thread team, and stages are chained into multi-stage pipelines, for example PtychoNN stage 1 GPU inference feeding stage 2 CPU stitching.

Contribution to reproducibility. The artifact makes the paper's experiments reproducible end to end. All inputs are deterministic: inference uses only public pretrained models, and throughput runs replay PRNG-generated frames of the true input shapes, so no live detector is needed. Each benchmark starts its own nats-server, writes per-run logs and a summary.csv, and the plot scripts consume those CSVs to emit the exact paper figures. Bulky run directories are excluded from version control while the curated figure-source CSVs that regenerate every plot are included, so a reader can reproduce a figure either from a fresh run or from the archived data. Exact per-experiment commands are indexed in the artifact's experiments.md.

Reproducibility of Experiments

Environment. LLVM/Clang 20 or newer (C++20), CMake, CUDA 12.3, cuDNN 9.19; the XKRT runtime, yaml-cpp, the NATS C client with nats-server 2.11 or newer, and SWIG 4.4.1; free-threaded CPython 3.13 with TensorFlow 2.20, Keras 3.12, NumPy 2.3, nats-py, and PyYAML. The PtychoNN baseline additionally needs pvapy 5.6.0; the configuration search needs ytopt. CPU energy requires a usable perf exposing power/energy-pkg/ with kernel.perf_event_paranoid set to 1 or lower. Experiments run on one GPU node; the paper used a dual-socket AMD EPYC 7532 with 256 GB and one A100-PCIE-40GB.

Build. Build Drava with CMake by running, from a build directory, CC=clang CXX=clang++ cmake -DCMAKE_BUILD_TYPE=Release .. followed by make -j, and add the build directory to PYTHONPATH. The artifact is released under an anonymized link for double-blind review.

Experiment workflow. Every experiment follows the same two-step workflow, with exact commands indexed in the artifact's experiments.md. First, a benchmark driver runs the pipeline, starting its own nats-server when needed, sweeps the relevant knob, and writes per-run logs and a summary.csv to a timestamped directory. Second, a plot script consumes that CSV, or the archived curated CSV, and emits the PDF/PNG figure. Each experiment maps to one article result: the message-rate ceiling produces the runtime message-rate ceiling figure; the PvaPy versus Drava single- and two-stage comparison produces the combined PvaPy-vs-Drava figure; the PvaPy HPC distributor sweep produces the distributor scaling figure; the manual configuration sweep produces the throughput-vs-latency figure; the observability sweep produces the runtime observability figure; the TomoGAN energy experiment produces the energy-efficiency figure; and the agentic search produces the ytopt convergence figure and the top-configuration table.

Execution time. A single benchmark point runs in seconds to a few minutes; a full experiment sweep across all knob values with repeated runs takes minutes to about one hour; and reproducing the entire figure set at high repetition takes a few hours on the reference node.

Expected results and mapping to the article. Each driver and plot script pair regenerates the same figure, in the same format, as in the article, so verification is a direct visual and numerical comparison. The message-rate ceiling reproduces the roughly 31k frames per second plateau. The PvaPy comparison shows Drava staying loss-free while PvaPy drops frames beyond 2 kHz, up to 2.36 times higher single-stage and about 1.5 times higher two-stage throughput. The distributor sweep shows throughput falling and latency rising with consumer count while Drava is about 2.6 times faster. The manual and observability sweeps show the best end-to-end configuration differing from the GPU-optimal one, up to 2.44 times. The TomoGAN run shows the non-monotonic energy-efficiency trend. The agentic search reaches 2.24 times over the best manual configuration while sampling 0.52 percent of the space. Small run-to-run variation is expected, so quantitative results are reported as the mean over repeated runs, while qualitative trends and relative comparisons are stable across runs.
