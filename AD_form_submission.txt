ARTIFACT IDENTIFICATION
============================================================

CONTRIBUTIONS AND ROLE OF THE ARTIFACT
--------------------------------------
This paper contributes Drava, an event-driven runtime for edge scientific
streaming pipelines, together with (i) its callback-based programming model,
(ii) a runtime that owns microbatching, dispatch, transport, placement, and
per-stage observability, (iii) an agentic (ytopt) configuration search, and
(iv) an evaluation on PtychoNN ptychography and TomoGAN tomography against a
PvaPy baseline. The computational artifact realizes every one of these claims:
it contains the Drava runtime (C/C++ on the XKRT tasking runtime with Python
bindings), the two application pipelines, a PvaPy single-record and
HPC-distributor baseline for PtychoNN, the agentic search driver, and the
benchmark and plotting scripts that regenerate each figure and table in the
paper. Running the artifact reproduces the throughput, end-to-end latency,
GPU+CPU energy, and configuration-search results reported in the Evaluation
section.

SOFTWARE ARCHITECTURE
---------------------
Drava is a layered runtime. Applications register per-stage callbacks through a
C or Python API; a YAML configuration binds each stage to its transport,
batching policy, and thread team without changing application code; and an
execution engine performs I/O, microbatching, work-stealing task dispatch, and
metrics collection. Stages exchange events -- each a unique identifier,
timestamp, and payload -- over two interchangeable transports: Unix sockets for
intra-node communication and NATS JetStream (publish/subscribe) for streaming
across nodes. Each stage runs as a process with an internal thread team, and
stages are chained into multi-stage pipelines (e.g., PtychoNN stage 1 GPU
inference -> stage 2 CPU stitching).

CONTRIBUTION TO REPRODUCIBILITY
-------------------------------
The artifact makes the paper's experiments reproducible end to end. All inputs
are deterministic: inference uses only public pretrained models, and throughput
runs replay PRNG-generated frames of the true input shapes, so no live detector
is needed. Each benchmark starts its own nats-server, writes per-run logs and a
summary.csv, and the plot scripts consume those CSVs to emit the exact paper
figures. Bulky run directories are excluded from version control while the
curated figure-source CSVs that regenerate every plot are included, so a reader
can reproduce a figure either from a fresh run or from the archived data. Exact
per-experiment commands are indexed in the artifact's experiments.md.

REPRODUCIBILITY OF EXPERIMENTS
============================================================

ENVIRONMENT
-----------
LLVM/Clang >= 20 (C++20), CMake, CUDA 12.3, cuDNN 9.19; the XKRT runtime,
yaml-cpp, the NATS C client with nats-server 2.11+, and SWIG 4.4.1;
free-threaded CPython 3.13 with TensorFlow 2.20, Keras 3.12, NumPy 2.3,
nats-py, and PyYAML. The PtychoNN baseline additionally needs pvapy==5.6.0;
the configuration search needs ytopt. CPU energy requires a usable perf
exposing power/energy-pkg/ (kernel.perf_event_paranoid <= 1). Experiments run
on one GPU node (paper: dual-socket AMD EPYC 7532, 256 GB, 1x A100-PCIE-40GB).

BUILD
-----
Build Drava with CMake:
    CC=clang CXX=clang++ cmake -DCMAKE_BUILD_TYPE=Release ..
    make -j
and add the build directory to PYTHONPATH. The artifact is released under an
anonymized link for double-blind review.

EXPERIMENT WORKFLOW
-------------------
Every experiment follows the same two-step workflow, with exact commands
indexed in the artifact's experiments.md. (1) A benchmark driver runs the
pipeline (starting its own nats-server when needed), sweeping the relevant knob,
and writes per-run logs and a summary.csv to a timestamped directory. (2) A plot
script consumes that CSV (or the archived curated CSV) and emits the PDF/PNG
figure. Each experiment maps to one article result:
- Message-rate ceiling                 -> runtime message-rate ceiling figure
- PvaPy vs Drava (single/two-stage)    -> combined PvaPy-vs-Drava figure
- PvaPy HPC distributor                -> distributor scaling figure
- Manual config sweep                  -> throughput-vs-latency figure
- Observability sweep                  -> runtime observability figure
- TomoGAN energy                       -> energy-efficiency figure
- Agentic search                       -> ytopt convergence figure + top-config table

EXECUTION TIME
--------------
A single benchmark point runs in seconds to a few minutes; a full experiment
sweep (all knob values, repeated runs) takes minutes to ~1 h, and reproducing
the entire figure set at high repetition takes a few hours on the reference node.

EXPECTED RESULTS AND MAPPING TO THE ARTICLE
-------------------------------------------
Each driver/plot pair regenerates the same figure, in the same format, as in the
article, so verification is a direct visual and numerical comparison. Concretely:
the message-rate ceiling reproduces the ~31k frames/s plateau; the PvaPy
comparison shows Drava staying loss-free while PvaPy drops frames beyond 2 kHz
(up to 2.36x single-stage, ~1.5x two-stage); the distributor sweep shows
throughput falling and latency rising with consumer count while Drava is ~2.6x
faster; the manual and observability sweeps show the best end-to-end
configuration differing from the GPU-optimal one (up to 2.44x); the TomoGAN run
shows the non-monotonic energy-efficiency trend; and the agentic search reaches
2.24x over the best manual configuration while sampling 0.52% of the space. Small
run-to-run variation is expected, so quantitative results are reported as the mean
over repeated runs; the qualitative trends and relative comparisons are stable
across runs.
